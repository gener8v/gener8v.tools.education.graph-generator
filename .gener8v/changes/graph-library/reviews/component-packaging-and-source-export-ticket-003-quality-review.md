### QR-002: `Layout` takes `DescriptionBase`, so a layout cannot be typed by its own description the way `GraphTypeDefinition<D>` and `DomainCheck<D>` are

**Category:** Patterns
**Severity:** Suggestion
**Location:** `src/layout/registry.ts:8`; `src/react/createGraphComponent.tsx:58-62` (`GraphTypeParts`); `tests/fixtures/layouts.ts:12`, `tests/fixtures/layouts.ts:21`; the established pattern in `src/core/definitions/types.ts:198-227`
**Description:**
- **The established pattern.** The definition contract is generic over the normalized description: `GraphTypeDefinition<D>`, `DomainCheck<D>`, `describe(normalized: D)`. It uses method syntax so that a definition typed for one graph type still fits the registry, which is typed by `DescriptionBase` (the comment at `src/core/definitions/types.ts:207-208`). The fixture circle uses it: `GraphTypeDefinition<Circle>` (`tests/fixtures/definitions/circle.ts`).
- **The new contract.** `Layout`, added here, is a plain function type over `DescriptionBase`, so it does not follow that pattern. Type-check probe on a scratch file with the repo's strict options:
  - `const typed: Layout = (normalized: Circle): Scene => …` fails with TS2322: "Property 'radius' is missing in type 'DescriptionBase' but required in type 'Circle'."
  - `const untyped: Layout = (normalized) => … normalized.raduis as number …` compiles. The misspelt field is not caught.
- **The consequence.** Every layout must cast its fields one by one, as the fixture does (`normalized.radius as number`, `tests/fixtures/layouts.ts:21`). `GraphTypeParts` also cannot check that a per-type component's definition and layout describe the same type.

**Impact:**
- Eleven layouts are about to be written, and GSS TICKET-002 is the one the others copy.
- Layouts are where the package's main correctness risk lives: the mathematics. With this contract, a misspelt or renamed field there compiles, and it shows up only if some test happens to draw that path.
- A later change to `Layout` would stay compatible, through a default type argument. But by then the casts would already have been copied into every layout.

**Recommendation:** Give `Layout` the same shape as the definition contract. Method-syntax bivariance keeps it a plain function type:

```ts
// Method syntax keeps the parameter bivariant, as GraphTypeDefinition.describe does, so a layout
// typed for one graph type still fits the shared table.
export type Layout<D extends DescriptionBase = DescriptionBase> = { draw(normalized: D): Scene }["draw"];

export interface GraphTypeParts<D extends DescriptionBase = DescriptionBase> {
  definition: GraphTypeDefinition<D>;
  layout: Layout<D>;
}
```

This was checked on a scratch file:
- a `Layout<Circle>` assigns to a `Layout` table;
- a misspelt field is a type error;
- a `Layout<Other>` paired with a `GraphTypeDefinition<Circle>` in `GraphTypeParts<Circle>` is refused.

Then type the fixture layout as `Layout<Circle>` (exporting the fixture's `Circle` interface) and drop its casts.

**Status:** Resolved
**Resolution:** Fixed (Thomas, 2026-10-11).
- `Layout<D extends DescriptionBase = DescriptionBase>` uses method-syntax bivariance.
- `GraphTypeParts<D>` is generic, and so is `createGraphComponent<T, D>`. The widening to the shared table types happens in one place.
- The fixture layout is typed `Layout<Circle>` with no casts.

`@ts-expect-error` tests cover a misspelt field and a square layout paired with the circle definition.

### QR-003: The documented `createGraphComponent(...)` line has no `/* @__PURE__ */`, so whether `.` consumers drop unused per-type components depends on how tsup chunks the build

**Category:** Performance
**Severity:** Suggestion
**Location:** `src/react/createGraphComponent.tsx:77-79` (the usage line in the TSDoc), `src/react/createGraphComponent.tsx:82`; `tests/package/per-type-bundle.test.ts:47-56`; `tsup.config.ts:4-5`
**Description:**
- **Why the call is kept.** Each per-type file will be one top-level call: `export const CircleGraph = createGraphComponent("circle", { … })`. A bundler keeps a top-level call it cannot prove pure, even when its result is unused. This factory also throws on a mismatched definition. The CR-002 fix marked the layout table's construction `/* @__PURE__ */`, but not the call every per-type file will repeat.
- **A declaration-level mark does not help.** Marking the declaration `/* @__NO_SIDE_EFFECTS__ */` made no difference in a probe: esbuild 0.28.2 does not carry that mark across modules.
- **Probes.** All used the repo's esbuild 0.28.2 and tsup 8.5.1 with `tsup.config.ts`'s options (`splitting`, Rollup `treeshake`, `platform: "neutral"`), building into the scratchpad. Each build added two marker per-type components in memory. A consumer bundle then imported only `{ CircleGraph }` from the built `dist/index.js`, with `sideEffects: false`.
  - **Separate per-type modules, no per-type entries.** Both components are inlined into `dist/index.js`, and the consumer keeps the number-line component and its layout. With `/* @__PURE__ */` on each call, it is dropped.
  - **Separate modules plus one tsup entry per type,** as `tsup.config.ts:4-5` says each type ticket adds. Each component gets its own chunk, and the consumer drops the unused chunk whether or not the call is marked.
- **The bundle test covers neither case.** `tests/package/per-type-bundle.test.ts` bundles one component per entry.

**Impact:**
- Nothing ships yet. Once types land, `import { CircleGraph } from "@gener8v/graph-generator"` stays small only while every type has its own tsup entry and the chunking stays as it is.
- If a type lands without its entry, or a tsup or esbuild change merges chunks, every `.` consumer silently pays for every type. AD-001 says "a consumer importing one graph type must not pay for the others".
- Nothing would show it unless TICKET-004's size checks measure `.` with a single named import.

**Recommendation:**
- Make the documented line:

  ```ts
  export const CircleGraph = /* @__PURE__ */ createGraphComponent("circle", { definition: circle, layout: circleLayout });
  ```

  Use it in the factory's TSDoc and, during resolution, in the GSS TICKET-002 Known Hazard that shows the line.
- Add a bundle case with two components defined in one module, where the entry imports one, asserting the other's marker is absent. The case fails without the mark.
- Optionally, add a check that every `src/react/graphs/*.tsx` file matches `= /* @__PURE__ */ createGraphComponent(`.

**Status:** Resolved
**Resolution:** Fixed (Thomas, 2026-10-11).
- The factory's TSDoc and the GSS TICKET-002 Known Hazard show `export const CircleGraph = /* @__PURE__ */ createGraphComponent(...)`.
- A new bundle case defines two marked components in one module and imports one. It asserts the other's layout is absent; removing the mark fails it.

### QR-007: Every per-type component is named `TypedGraph`, so DevTools and error component stacks cannot tell the types apart

**Category:** Observability
**Severity:** Suggestion
**Location:** `src/react/createGraphComponent.tsx:87-93`
**Description:** The factory returns the same inner function name for every graph type. So the following all name a per-type component `TypedGraph`:
- React DevTools;
- React's development warnings;
- the `componentStack` an error boundary receives.

`Graph` has its own name. The exports `CircleGraph` and so on are named in the source, but not at runtime. Under DEL-004, an error from a consumer's `fallback` function propagates through the component. The consumer's error boundary then reports `at TypedGraph` whether the circle, the number line or the pictograph component was rendering.

**Recommendation:** Set a display name from the type inside the factory, for example ``TypedGraph.displayName = `Graph(${type})` ``, or `<Pascal>Graph` to match the exported names. It adds no markup, so markup equality with `Graph` (CPSE-REQ-010) is unaffected. Add a one-line test.
